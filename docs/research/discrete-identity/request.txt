
# Cheddar GPU — Discrete CKKS Reproduction and MEBOOT Identity Integration
# Autonomous Research and Implementation Task
#
# Objective:
# 1. Faithfully reproduce the CCS 2025 Discrete CKKS high-precision
#    identity bootstrapping method on the existing Cheddar GPU codebase.
# 2. Establish an independently validated Cheddar-native baseline.
# 3. Integrate MEBOOT's four-role C2S construction and low-q0P entry
#    key switching into that baseline.
# 4. Reuse Cheddar's existing high-performance GPU kernels and fusion
#    infrastructure wherever semantically compatible.
# 5. Deliver correct, reusable, robust implementations and matched
#    GPU measurements, not a one-off experiment.

Primary sources:

[Discrete CKKS]
https://eprint.iacr.org/2025/1786
"Leveraging Discrete CKKS to Bootstrap in High Precision"
Choe, Kim, Stehlé, Suvanto, ACM CCS 2025.

[Cheddar]
https://github.com/scale-snu/cheddar-fhe

[MEBOOT]
The authoritative implementation, source-binding documents,
security parameter records, and latest manuscript in the current
project.

IMPORTANT:
The existing Cheddar checkout is the implementation target.
Locate its actual path, branch, commit, build configuration, and
GPU runtime before doing anything destructive.

The MEBOOT implementation may be in a separate repository.
Treat its mathematics and validated state transitions as authoritative,
but adapt them to Cheddar's representation instead of copying
CPU-oriented code directly.

This task requires IMPLEMENTATION, not merely a feasibility report.

==========================================================
0. NON-NEGOTIABLE ENGINEERING RULES
==========================================================

- Preserve existing working trees and experiments.
- Do not modify frozen MEBOOT or RBOOT evidence.
- Do not change Cheddar's established public APIs unnecessarily.
- Do not rewrite existing optimized kernels without evidence.
- Do not introduce a separate FHE runtime inside Cheddar.
- Do not duplicate existing NTT, key-switch, polynomial-evaluation,
  basis-conversion, rescale, or bootstrap infrastructure.
- Do not claim that a plaintext simulation is an HE reproduction.
- Do not change precision/security thresholds after seeing results.
- Do not run large GPU campaigns before small correctness gates pass.
- Never relax security to make an experiment execute.
- Do not silently fall back to CPU during timed GPU evaluation.
- Do not claim success from test execution without verifying decrypted
  outputs against an independent mathematical reference.

Create a dedicated, non-destructive research branch or worktree.

Keep both implementations selectable:

    DiscreteIdentityBaseline
    MEBOOTDiscreteIdentity

No unconditional changes to the existing Cheddar Boot() behavior.

Build an operation-inventory table.

EXISTING:
    already available and correct for the required semantics;

EXTENSIBLE:
    available but missing required parameter/range support;

MISSING:
    requires a new operator;

INCOMPATIBLE:
    cannot represent the required operation without architecture changes.

Locate real kernel entry points and their callers.

Do not assume a kernel or API exists merely because a paper mentions it.

Record which existing Cheddar kernels can support:

- direct DigitExtract polynomial evaluation;

- MEBOOT M1/M2/M3/M4;

Run the current upstream unit and bootstrap tests before modifying code.

Save baseline correctness and performance results.

2. INDEPENDENTLY RECONSTRUCT DISCRETE CKKS
==========================================================

Read the CCS 2025 primary PDF thoroughly.

Derive an implementation specification directly from the paper.

Cover:

A. StC-first EvalRound+ architecture;

B. raised integer representation:
       z = I + epsilon;

C. direct digit extraction;

D. indirect digit extraction, if required for completeness
   or comparison;

E. bit/trit representation and signed-integer conventions;

F. iterative digit cleaning;

G. clean digit recombination;

H. Thrifty computation;

I. Grafting and heterogeneous precision;

J. accurate C2S bypass;

K. final identity reconstruction;

L. scale, modulus, numerical-error, and security requirements.

Distinguish:

PAPER-EXPLICIT:
    directly specified by the paper;

DERIVED:
    established by mathematical derivation;

IMPLEMENTATION CHOICE:
    selected by us because the paper leaves flexibility;

UNRESOLVED:
    insufficient source information.

For all relevant equations, document their section/page references.

Use official author code as secondary evidence only if provenance is verified.

Do not derive Discrete CKKS behavior from Cheddar's existing comments.

==========================================================
4. REUSE CHEDDAR'S HIGH-PERFORMANCE KERNEL FUSION
==========================================================

This is a major engineering requirement.

Cheddar's fused kernels and operation scheduling should remain the
performance foundation of the implementation.

Before creating any new CUDA kernel, search for a compatible existing
primitive or fusion path.

Prioritize reuse of:

- optimized NTT/INTT;
- RNS modular arithmetic;
- basis conversion;
- key switching;
- ciphertext/plaintext multiplication;
- relinearization;
- fused rescale;
- fused polynomial evaluation;
- batched scalar operations;
- existing BSGS and hoisting;
- GPU temporary-buffer management.

Investigate fusion opportunities for:

1. Polynomial-evaluation multiply/add/rescale sequences.

2. Repeated bit-cleaning iterations.

3. Per-digit independent polynomial evaluation.

4. Recombination of cleaned digits.

5. MEBOOT linear-transform and key-switch sequences.

6. Grafting-compatible scale transitions.

Optimize actual dataflow.

Avoid intermediate global-memory round trips when existing fusion
infrastructure can eliminate them.

However, NEVER fuse across an operation boundary if doing so changes
rounding, rescaling, key-switching, or numerical-error semantics.

Maintain a simple, independently testable execution path before enabling
aggressive fusion.

==========================================================
5. GPU EXECUTION DESIGN
==========================================================

Discrete CKKS digit extraction produces several independent ciphertexts.

Use GPU parallelism intelligently.

Investigate:

- parallel digit evaluation;
- shared powers for polynomial evaluation;
- common subexpression reuse;
- batched cleaning;
- scheduling of independent digit pipelines;
- reuse of polynomial plaintext constants;
- reuse of NTT-transformed operands;
- stream/event dependencies;
- peak temporary allocation.

Do not assume that launching more streams is automatically faster.

Profile occupancy, memory traffic, kernel-launch overhead, synchronization,
and GPU memory pressure.

Avoid repeated host-device copies.

Do not synchronize the entire device after each elementary operation
unless correctness requires it.

Ensure deterministic dependency ordering and lifetime safety.

==========================================================
7. HIGH-PRECISION BACKEND COMPATIBILITY
==========================================================

Cheddar uses a GPU-oriented RNS representation.

The CCS 2025 method requires heterogeneous scales and precision growth.

Audit whether the existing representation supports:

- all required scale ratios;
- sufficiently accurate polynomial coefficients;
- Grafting operations;
- all necessary temporary moduli;
- rescale rounding;
- high-precision slot encoding/decoding;
- the paper's polynomial-evaluation accuracy.

Do not equate a large symbolic CKKS scale with actual available
numerical precision.

If original 81-bit replication requires unsupported host-side precision,
introduce the smallest reusable high-precision reference/preprocessing
component compatible with Cheddar.

Keep the runtime GPU-native.

If the paper's complete high-precision configuration is impossible under
current backend constraints, report the precise blocker and preserve any
validated moderate-precision baseline.

Never claim an 81-bit reproduction from an 18-bit experiment.

==========================================================
9. NOW INTEGRATE MEBOOT INTO DISCRETE IDENTITY
==========================================================

Do not modify DigitExtract, VecClean, or integer recombination merely
to make MEBOOT integration easier.

Reuse the validated baseline modules.

Replace the original low-precision C2S implementation with MEBOOT's
four-role realization:

    M1:
        subring-secret key-free prefix;
        temporary q* modulus;

    M2:
        direct LCR/AKS transition;
        subring secret -> application secret;
        level conserving;

    M3:
        dense BSGS factor;
        one main-chain rescale;

    M4:
        dense BSGS factor;
        one main-chain rescale.

Keep the accurate bypass as a separate branch.

The target ideal reconstruction is:

    z_low  = I + epsilon + e_low
    z_high = I + epsilon + e_high

    I_clean = CleanInteger(z_low)

    y = z_high - I_clean

followed by the specified output normalization.

The subtraction is valid ONLY after both branches are aligned to the same
physical units.

The MEBOOT integration must explicitly preserve:

- identical integer representative I;
- compatible secret state;
- correct main-Q fork;
- correct auxiliary q* removal;
- correct LCR reconstruction;
- compatible scale/level;
- correct packing;
- precise final output state.

Do not introduce an implicit modulus-down or rescale in the bypass fork.

Keep distinct:

- residual q0;
- entry auxiliary P_ent;
- main hybrid-switching P;
- MEBOOT temporary q*;

Audit:

- gadget digit correctness;
- top-digit handling;

- RNS basis conversions;
- integer lifts;
- rounding;

- GPU fusion compatibility;
- full public parameter/security exposure.

Reuse optimized kernels where possible.

Do not implement a standalone, incompatible GPU key-switch framework.

==========================================================
11. HW40 INTEGER DOMAIN AND DIGIT WIDTH
==========================================================

The previous MEBOOT EC21 model suggests:

    H = 40
    K = 20
    6-bit signed integer representation

as a candidate configuration for strong integer-domain reliability.

Reverify this independently.

Specifically check:

- exact integer range and signed convention;
- Irwin-Hall or paper-specific distribution assumptions;
- the number of coefficients covered by the failure event;
- per-call and repeated-call union bounds;
- entry-switch-induced noise and bias;
- correlation introduced by subring lifting;
- the correctness of treating H as the effective secret weight.

Target:

    integer-domain failure probability <= 2^-128

under an explicitly documented model.

Do not confuse this probability with overall RLWE security.

Also do not confuse:

    6 extracted bits

with:

    6 multiplicative levels.

The actual DigitExtract depth must be obtained from the constructed
polynomial evaluation graph.

==========================================================
12. TARGET PRECISION: STRICTLY GREATER THAN 18 BITS
==========================================================

The primary MEBOOT-integrated Identity target is:

    complete refreshed output precision > 18 bits.

This is not an 80-bit requirement.

However, the original Discrete CKKS high-precision reproduction must
remain independently documented and testable.

For the MEBOOT target, investigate:

- direct six-bit digit extraction;
- two cleaning iterations;
- three cleaning iterations if necessary;
- alternative extraction schedules that preserve correctness.

Do not assume the six-bit extractor has the same degree/depth as the
paper's five-bit extractor.

Determine the actual polynomial degree, multiplicative depth, and
approximation error.

Measure input precision to DigitExtract.

Derive or numerically verify the effective:

    g = q0 / Delta_effective

for the actual normalized input.

Do not infer g from ciphertext metadata alone.

Select the shallowest validated circuit that exceeds the output
precision requirement under the declared input domain.

==========================================================
18. SCIENTIFIC SUCCESS CRITERIA
==========================================================

Evaluate three separate questions.

RQ1:
Can Cheddar faithfully reproduce Discrete CKKS integer cleaning and
identity bootstrapping?

RQ2:
Can MEBOOT's low-q0P subring prefix and four-role C2S be integrated
without breaking the numerical, scale, secret, and integer interfaces?

RQ3:
At output precision >18 bits and the required security level, does
MEBOOT improve the complete Discrete Identity resource tradeoff?

Possible positive results:

- one fewer main-chain C2S rescale;
- lower complete EVK;
- reduced online latency;
- improved remaining modulus;
- reduced matrix/arithmetic cost.

Possible negative results:

- increased DigitExtract depth;
- more cleaning iterations;
- higher entry noise;
- more evaluation keys;
- larger temporary memory;
- added kernel-launch overhead;
- no complete-bootstrap benefit.

Report all outcomes honestly.

Do not optimize only a favorable substage.
