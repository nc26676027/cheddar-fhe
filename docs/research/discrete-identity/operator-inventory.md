# Phase 0 operator inventory: Discrete CKKS identity

Scope: this checkout and the acquired [Cheddar GPU paper](../../../build/research/cheddar-2407-13055.pdf), Choi et al., *Cheddar: A Swift Fully Homomorphic Encryption Library Designed for GPU Architectures*, ASPLOS 2026. Page numbers below are PDF pages (1-based). `EXISTING` means a callable implementation is present, not that the CCS 2025 Discrete CKKS circuit has been reproduced. `EXTENSIBLE` means the kernel can plausibly serve a derived stage with new orchestration. `MISSING` means no matching operator was found in `include/`, `src/`, or the root CMake source lists. `INCOMPATIBLE` marks a verified contract that cannot be used as is. The acquired paper is Cheddar's original GPU paper, **not** the Discrete CKKS primary paper; Discrete CKKS arithmetic, depth, accuracy, and security remain to be derived from that separate source.

## Minimal new work implied by this audit

1. Derive and implement the **Discrete CKKS identity graph**: encrypted DigitExtract, VecClean, digit recombination, required transform ordering, scale/level schedule, and separate original-baseline and MEBOOT-integrated drivers. This is orchestration plus paper-specific constants/polynomials, not evidence of a new NTT, multiplication, or key-switch kernel.
2. Resolve any **Discrete CKKS scale or modulus transition** against its own paper equations. First map it to Cheddar's existing `level_config` and `Rescale`/`ModDownAndRescale`, checking exact ratio, rounding, key basis, and output scale. Grafting is a distinct power-of-two-base scheme, not a synonym for Cheddar RR. A new GPU kernel is not justified by the current evidence.
3. If an exact 81-bit encoding contract is required, add a precision-safe coefficient construction path (for example integer limbs/residues before upload) rather than feeding an 81-bit value through `double`. A high output scale alone does not prove 81-bit precision.
