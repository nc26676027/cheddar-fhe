# Minimal high-precision host backend plan

This is a **plan**, not an implemented precision claim. It compares the acquired [Cheddar GPU paper](../../../build/research/cheddar-2407-13055.pdf) with this checkout. Paper page numbers are 1-based PDF pages. The CCS 2025 Discrete CKKS paper remains a separate required source for its exact identity graph, scaling equations, and 81-bit metric.

## What Cheddar already supplies

Cheddar describes 32-bit main/terminal-prime rational rescaling in Section 3 (PDF pp. 4-5), inverted-terminal layout on p. 6, and fused rescale/ModDown in Section 5.1/Fig. 4 (pp. 7-8). The checkout implements those mechanisms: `Parameter::Parameter` validates ordered `level_config` and builds a reversed-terminal/main-prime basis (`src/core/Parameter.cu:84-143`), computes the rescale numerator/denominator from primes added and removed (`:176-218`), and `ModSwitchHandler` prepares removed/restore-prime constants (`src/core/ModSwitch.cu:372-526`). `ModDownWorker` uses the componentwise minimum source/destination basis and fused epilogue (`:805-920`). `Context::Rescale` and `ModDownAndRescale` are the existing device entry points (`src/core/Context.cpp:695-716`). Thus **no new rational-rescale GPU kernel is the default plan**.

Cheddar's paper calls Grafting a *different*, power-of-two-base RNS construction and explains its GPU NTT cost (PDF p. 5, Section 3.2). If the Discrete CKKS paper calls for Grafting's *effect* (a modulus/scale transition), first express the same numeric map using Cheddar's declared main/terminal-prime schedule. Equivalence requires the same input/output modulus and scale to the required tolerance, compatible evaluation-key basis, bounded rounding error, and a verified level ordering. `CompareNPPair` requires increasing total prime count (or, if tied, increasing main count) across configured levels (`src/core/Parameter.cu:10-15,84-117`); the rescale constructor requires one prime family to decrease while the other may increase (`src/core/ModSwitch.cu:372-424`). If those conditions fail, document the exact mismatch before proposing a kernel. Metadata relabeling by `SetScale` is not an arithmetic transition (`src/core/Container.cpp:18`).

## Actual host precision loss

| Path | Source | Limit and minimum remedy |
| --- | --- | --- |
| Slot encode and special IFFT | `include/core/Type.h:13`; `src/core/Encode.cpp:15-21,26-42,87-111,138-194` | Inputs/twiddles and every butterfly are `std::complex<double>`. At a large scale, `double` rounding happens **before** BigInt or RNS. Add a separate binary128 complex path for high-precision preprocessing, including twiddles and butterflies; keeping the FFT in double would defeat a binary128 final conversion. |
| Coefficient-to-integer and constant encode | `src/core/Encode.cpp:164-185,257-281`; `src/core/BigInt_tommath.cpp:22-25` | `value = number * scale` and `std::round` use double; `BigInt(double)` calls `mp_set_double`. Add a binary128 input/scale path, `roundq` with the existing nearest-integer tie rule, and **exact transfer of the rounded integer** into TomMath before residue extraction. An 81-bit integer must never pass through `double` or `uint64_t`. |
| Decode and reference output | `src/core/Encode.cpp:48-83,199-253`; `src/core/BigInt_tommath.cpp:52` | iCRT is BigInt, but `GetDouble()/scale` and special FFT return double. Add binary128 conversion **after** centered iCRT and a binary128 special FFT for reference/oracle/decrypted checks. Keep this host path offline; no host decode in encrypted evaluation. |
| Prepared polynomial/diagonal data | `include/extension/EvalPoly.h:181-198`; `src/extension/EvalPoly.cpp:482-525`; `include/extension/StripedMatrix.h:11`; `src/extension/LinearTransform.cu:329-340` | `EvalPoly` coefficients and all scale planning are double; transform diagonals are `Complex`/double. A high-precision oracle alone does not fix plaintext preparation. Where the derived circuit needs more than double coefficient accuracy, preserve binary128 coefficients and scales through compilation and encode, and prepare high-precision diagonals before upload. Keep existing compiled CUDA kernels and their RNS plaintext format. |
| Scale metadata | `include/core/Container.h:16-18`; `include/core/Parameter.h:65,263-264`; `src/core/Parameter.cu:176-218`; `src/core/Context.cpp:54-60` | Runtime scales/rescale ratios are double, and `AssertSameScale` accepts relative `1e-12`. Exact powers of two can be represented, but arbitrary accumulated ratios cannot certify 81-bit output precision from these metadata alone. For a high-precision route, carry an exact prime-product/rational scale or binary128 scale ledger through affected preprocessing and reference calculations; retain the public double API for existing routes. Prove any conversion back to double harmless for the specific operation, or extend that operation's scale contract. |

The paper says Cheddar supports high-precision bootstrap algorithms and uses larger bootstrap scales (PDF p. 9, Sections 6-7), but it does **not** assert this checkout's host encoder or an 81-bit Discrete CKKS identity result. The 53-bit significand of double is the local input bottleneck. Binary128 has 113 significand bits, so it is a plausible minimum for an 81-bit target, subject to a measured/bounded FFT, polynomial, scale, and CKKS noise ledger; `2^81` as a scale by itself is not 81 bits of output accuracy.

## Smallest implementation seam to evaluate later

1. Build a **host-only, opt-in** high-precision helper around GCC `__float128` and `libquadmath` for the research route. The WSL environment exposes `quadmath.h` and `libquadmath.so`; `sinq`/`cosq` or `sincosq` can generate twiddles, `roundq` matches the current nearest-integer behavior, and `strtoflt128`/`quadmath_snprintf` handle decimal interchange. Use a dedicated pair of binary128 real/imag values rather than assuming `std::complex<__float128>` is fully supported by the C++ library. Add only the necessary CMake link for this host helper when implemented; do not change CUDA device arithmetic.
2. Reuse the current special-FFT index/order algorithm (`src/core/Encode.cpp:87-135`) with binary128 arithmetic and the same Galois-factor table. Keep the ordinary `Encoder` and public `Complex` API intact. Expose opt-in high-precision encode/decode/preprocess calls for the research route, emitting the same `Plaintext<uint64_t>`/`Constant<uint64_t>` residues and NTT form that Cheddar's GPU operators consume. Reuse `src/core/NTT.cu:607,674` and device uploads in `src/core/DeviceVector.cpp:103-120`.
3. Extend `BigInt` minimally for **lossless decimal-integer interchange**, not a new big-integer backend. For `USE_GMP=OFF`, TomMath offers `mp_read_radix` and `mp_to_radix`; GMP has `mpz_set_str`/`mpz_get_str` for the optional build. After `roundq`, format a finite integral binary128 value with `quadmath_snprintf("%.0Qf", ...)`, parse it to signed BigInt, then reuse `BigInt::Mod` and `GetUnsigned` **only after reduction to one prime** (`src/core/Encode.cpp:173-185,266-277`). For decoding, serialize centered BigInt to decimal, parse with `strtoflt128`, divide by the high-precision scale, and run the binary128 FFT. Check formatting/parser bounds, sign, overflow, subnormals, and rounding; never cast the full coefficient to `uint64_t`.
4. Prepare polynomial coefficients and matrix diagonals in binary128 **only where the derived circuit requires it**. Current `EvalPoly`'s `vector<double>` and `StripedMatrix`'s `Complex` types lose extra bits before encode (`include/extension/EvalPoly.h:181-198`; `include/extension/StripedMatrix.h:11`). A sidecar high-precision compiler/preprocessor can initially emit the existing residue plaintexts/constants, but it must retain the same level/decomposition decisions and prove that no double coefficient or scale conversion occurs on the accuracy-critical path. Avoid a broad templating of all CUDA code.
5. Verify on CPU first with deterministic vectors: exact integer round trips above `2^53` and near `2^81`, signed halfway cases matching existing rounding, binary128 FFT/IFFT forward error over 32,768 slots, coefficient residue equality against independent TomMath integer arithmetic, and binary128 decode/reference agreement. Then audit every scale handoff and the final application-unit error ledger. These are future gates; no build or GPU test is part of this audit.

**Boundary of the proposal:** libquadmath fixes host floating-point preparation and reference precision; it does not fix insufficient RNS modulus, CKKS noise, polynomial approximation error, key-switch rounding, or a non-equivalent rational transition. Those need separate source-derived bounds and encrypted tests before an 81-bit claim.
